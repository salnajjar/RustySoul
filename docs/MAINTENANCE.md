# Database maintenance, quiet refreshes and idle Away

## Database maintenance

Settings > Database maintenance shows the main database size, write-ahead log size and reusable database pages. Choose **Optimize query performance** to update SQLite query-planner statistics and checkpoint the WAL, or **Compact database and restart** to repack pages/rebuild the database layout, then update statistics and checkpoint. Both stop application writers through the existing graceful restart path, run before opening the daemon's database connections and return to the signed-in browser session. Media, credentials/key, accounts, settings and retained records are preserved. Connections/transfers resume according to existing startup preferences.

Compaction uses SQLite VACUUM; optimization uses `PRAGMA optimize=0x10002` on a fresh connection. These are the mechanisms recommended in the [SQLite VACUUM](https://www.sqlite.org/lang_vacuum.html) and [ANALYZE/optimize](https://www.sqlite.org/lang_analyze.html) documentation. Better query plans depend on workload; no universal speed increase is promised. Reusable pages already serve future inserts without compaction, so ordinary indexing does not need frequent vacuuming.

Maintenance is serialized with backup creation, validation, downloads and restore. Staging checks free space (three main-database/WAL sizes for compaction, two for optimization, plus a 64 MiB floor); startup checks again after checkpointing. It takes an exclusive data-folder lock, validates integrity/foreign keys, checkpoints and makes a temporary private rollback copy. A running marker supports interrupted-operation recovery. On success it verifies integrity/relationships again, syncs and records the before/after/reclaimed bytes and elapsed time. Verified completion removes the temporary rollback copy so space is actually reclaimed. A crash during final cleanup resumes from its durable completion record; an interrupted running job recovers its rollback database and reports a failed operation with previous data intact. The credential key is never modified.

`maintenance-pending/` and `maintenance-last-result.json` are private daemon-owned operational files. The result persists outside SQLite so it survives database recovery. The UI retains and can dismiss the latest outcome. SQL work has a 30-minute progress deadline. Filesystem failures that prevent verified recovery stop startup with the original recovery copy retained; do not delete pending recovery files manually. Normal temporary storage is private to the data volume and is not a library/download location.

The Docker/Podman restart policy or supplied native systemd unit restarts exit 75. A manually launched bare executable must be started again after requesting maintenance; automatic supervisor detection is not available. No maintenance is scheduled automatically. Deploying this feature does not compact production data on its own.

Authenticated API: `GET /api/v1/maintenance` returns stats, stats_error, latest result, busy/pending/pending_id and whether restart requests are supported. `POST /api/v1/maintenance` accepts `{"action":"optimize"}` or `{"action":"compact"}`, returns a job ID and requests restart. The ID must match the latest completion record before an operation is displayed as complete. Normal first-account, session, CSRF, JSON bounds and backup-operation serialization apply. Stats reads use one bounded worker; SQL maintenance runs with writers stopped and no additional persistent worker.

## Library refresh banners

Library updates expose `library.trigger`: startup, manual, locations, filesystem or scheduled. The existing 60-second scheduled reconciliation stays silent across the site, with its dynamic stage/totals still visible in Settings > File locations & library. Startup, manual re-index, changed locations and filesystem-event scans show the banner when the existing banner preference is enabled. Scheduled work does not hide warnings/errors. Manual re-indexing immediately changes the reason to manual even if the previous scan was scheduled.

## Idle Away

Settings > Profile > Automatically set Away when idle enables a saved timeout from 1 to 1440 minutes. It defaults to disabled for existing and fresh profiles (`auto_away_minutes:0`). Clicks, typing, pointer motion, scrolling, touch and returning to a visible signed-in tab report activity. No key text, click target, screen coordinates or browsing history are sent or stored. Notifications use leading/trailing throttling at ten seconds, with an immediate coalesced wake-up when automatically Away.

The daemon owns a monotonic timer shared by all tabs. Browser notifications include only the age of the last genuine activity; a delayed/background event cannot overwrite newer activity or falsely claim recent input. Polling, SSE and transfer traffic are not user activity. Without an active browser, inactivity still moves Online to Away after the configured period. A fresh UI action clears automatic Away. Manually selected Away (including Away on startup) remains until explicitly changed. Manual Online restarts the idle timer. Disabling the option clears automatic Away; deliberate manual Away is retained. Disconnect/reconnect clears automatic state and starts a fresh timer. Normal existing optional Away replies apply while automatically Away as well.

Profile API/JSON adds `auto_away_minutes`; live snapshots add `away_automatic`. Normal command admission accepts `{"type":"ui_activity","idle_seconds":0}`; the age is limited to one day and defaults to zero. Activity commands preserve current system messages and do not create activity logs. The setting uses existing profile JSON, so schema 11 is unchanged.
