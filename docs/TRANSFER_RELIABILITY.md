# Transfer cancellation, timeouts and resumption

Uploads waiting on an established file socket check cancellation at half-second intervals. This covers sending the transfer handshake, waiting for the download resume offset and a receiver that stops accepting file data. Existing single-file, selected-file and whole-user cancellation controls use the same path. Acknowledged cancellation stays cancelled if a socket error or delayed connection timeout arrives later.

The resume-offset exchange has one 30-second deadline, even when a peer sends a few bytes and then stops. While sending file data, actual successful writes restart a 30-second inactivity budget. Waiting on RustySoul's own speed limits or reading the local file does not consume that peer budget. Poll timeouts retry without failing the upload or losing unsent data. Partial writes count only bytes accepted by the socket; unused total/per-user rate allowance is refunded. Resume offsets contribute to displayed file progress but not new all-time payload bytes.

Upload history distinguishes `timed_out` from `failed`, with readable reasons for unanswered offers, missing reverse connections, an incomplete offset exchange or a receiver that stops reading. Peer disconnects explain that the receiver left before completion. Expected peer timeouts/disconnects are warnings in Logs & activity, while local file errors remain errors. A peer control connection that cannot connect within 20 seconds is also a warning and does not mean the daemon has run out of threads.

Use the existing status filter and Clear history -> timed out to inspect/remove those records. Active/queued transfers, media files and lifetime traffic/graph totals are preserved. The downloader must request an upload again; RustySoul cannot force a remote client to retry.

Connection establishment remains separately bounded: direct dialing can take 20 seconds and reverse-connection negotiation has its existing 20-second deadline. Cancellation checks described above apply to established sockets; DNS resolution and blocked local filesystem calls are not made interruptible by this change. Upload-offer acknowledgement still has a 30-second deadline. This is not evidence of universal Internet reachability or full real-client interoperability.

## Download stalls, pause and partial resumption

A sending peer that stops delivering file data receives a 30-second inactivity budget, checked through one-second connected-socket polls. A real inactivity timeout now becomes `timed_out`, rather than a generic `failed` record. The partial remains for retry, the download slot is released, and existing timeout filters/history clearing/manual retry apply. Automatic retries remain enabled by default and use the saved bounded attempt/delay policy; while scheduled the visible state is `retry_waiting`. TCP connect and handshake I/O timeouts use the same timeout classification; local storage errors remain failures/storage holds.

Pausing keeps the current transfer connection and partial. One socket read may already be in flight; after that poll settles, disk writes stop until Resume. Time spent paused, waiting on our own speed limits or writing a local chunk does not consume the remote inactivity budget. Resume on the same connection continues; a failed partial explicitly retried after daemon restart requests its exact on-disk offset. Only newly read payload is added to lifetime counters, not the offset.

Cancellation signals the worker and cleans up its partial when its connected-socket poll settles. The worker retains its own parent-directory descriptor on Linux, so retiring the daemon's capability descriptor cannot strand cleanup. Idle cleanup must acquire the partial's file lock; active writers own their cleanup. Removal occurs while locked, with an inode/device identity check on Unix so an old worker cannot delete a replacement partial at that pathname. A missing retired download record is cancellation, rather than a false Token not found error. Unrequested late offers remain rejected. DNS, connection establishment and blocked filesystem calls retain the separate limits described above.

Expected remote disconnects, short transfers and timeouts are logged as warnings with the cause; actual local path/file/locking failures remain errors. `tests/fixtures/download_control.rs` drives independent P/F frames through pause/resume, cancelled paused data, a denied late offer, premature EOF, daemon restart and exact partial resumption, then verifies final bytes, durable counters and integrity. Independent-client coverage and remaining boundaries are documented in TESTING.md.


Transfer slot scheduling now distinguishes remote queue waits from accepted offers/active sockets. Remote waits do not starve other users. Atomic admission and a 30-second accepted-offer lease enforce local limits; offers deferred only for capacity return to waiting without network retry cost. Selected/per-user cancellation covers local waits, paused sockets and retry jobs without touching completed files. Local priority/manual order affects subsequent requests/offers and persists across restart. See TRANSFER_QUEUE.md.


Retained progress: each download attempt now shares an exact file-byte counter with its writer, including a resumed prefix. Failure, timeout and storage holds retain this count independently of periodic speed notifications; the final short fragment is included. Unopened retries preserve saved progress until a file is actually opened, and a known zero after truncation/recreation resets it. Counters are private to each attempt so old workers cannot change a retry. Terminal speeds stay zero. Both transfer lists show readable transferred/total bytes, with exact byte values available through the progress accessibility text and tooltip. These file progress values include resumed bytes; lifetime bandwidth counts only newly transferred payload. Abrupt shutdown still resumes from the actual partial on disk rather than trusting a saved UI count.


Empty files use the same offer, file-token and zero resume-offset handshake as other files, then complete without waiting for any payload or another EOF. Sharing, selection, history and readable destination paths include zero-byte files. They consume no payload bandwidth. The schema-13 download-table migration retains original rowids and every history field so default FIFO/manual queue order stays intact. Completed empty files show 100% progress; Open offers Save file without an audio decoder.


## Transfer timing

Upload and download rows display a local date/time beneath their status and a live `Elapsed HH:MM:SS` counter, with days for longer transfers. Completed, cancelled, failed, timed-out, blocked and interrupted transfers display a frozen total. Timestamps are persisted in SQLite and included in backups. The first observed active transfer starts the clock; pending queue time is excluded. Pauses and automatic retry waits are included as wall-clock time. A manual retry after a terminal result resets timing for the new attempt. Recovered interrupted transfers stop at the last saved live update, so daemon downtime is not added.

Older records are not backfilled from added/updated dates because those do not establish a real start. The UI shows timing as unavailable for that history. One shared browser clock updates mounted live rows; finished/collapsed rows do not add timers or API polling.
