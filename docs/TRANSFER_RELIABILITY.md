# Transfer cancellation, timeouts and resumption

Uploads waiting on an established file socket check cancellation at half-second intervals. Failed and cancelled Unix file streams use abortive close to discard unsent data, preventing retired transfers from draining in FIN-WAIT after their upload slots have been released. Successful streams keep a normal close after the payload has been acknowledged. This covers sending the transfer handshake, waiting for the download resume offset and a receiver that stops accepting file data. Existing single-file, selected-file and whole-user cancellation controls use the same path. Acknowledged cancellation stays cancelled if a socket error or delayed connection timeout arrives later.

The resume-offset exchange has one 30-second deadline, even when a peer sends a few bytes and then stops. While sending file data, successful writes or a decreasing Linux TCP output queue restart a 60-second inactivity budget. Kernel queue drain is acknowledged payload progress even when the application write remains blocked on send-buffer thresholds; zero-window probes alone do not reset the deadline. Linux completion waits for the output queue to drain, with cancellation checks, without requiring a peer FIN. Unsupported platforms retain write-based progress and completion. Waiting on RustySoul's own speed limits or reading the local file does not consume that peer budget. Poll timeouts retry without failing the upload or losing unsent data. Partial writes count only bytes accepted by the socket; unused total/per-user rate allowance is refunded. Resume offsets contribute to displayed file progress but not new all-time payload bytes.

Upload history distinguishes `timed_out` from `failed`, with readable reasons for unanswered offers, missing reverse connections, an incomplete offset exchange or a receiver that stops reading. Peer disconnects explain that the receiver left before completion. Expected peer timeouts/disconnects are warnings in Logs & activity, while local file errors remain errors. A peer control connection that cannot connect within 20 seconds is also a warning and does not mean the daemon has run out of threads.

Use the existing status filter and Clear history -> timed out to inspect/remove those records. Active/queued transfers, media files and lifetime traffic/graph totals are preserved. RustySoul can re-offer an originally requested upload; the receiver must accept and may decline it. RustySoul cannot force another client to receive data.

## Upload retries

New transient upload failures and timeouts are automatically scheduled using **Settings > Network settings > Transfer retries**. Uploads and downloads have separate enable switches and share the configured retry budget/delays. Both default to enabled. Retries increase their delay after each admitted attempt, wait for the recipient to be online or away, and expire after seven days. Waiting for an offline user takes no upload slot and consumes no attempt. The queue is bounded to 4096 saved retries, and status lookups are throttled. Admission respects global/per-user slots, queue ordering, bans and sharing protection. A fresh protocol offer, acceptance and resume-offset handshake precede any payload.

Use **Retry failed uploads** for saved historical failures, or **Retry failed** in one user's group. Historical failures are not all replayed on upgrade. A manual retry resets that file's retry budget. User cancellations, completed files, bans, missing shared files and permanent refusals are not automatically retried. Cancelling one file, a selection or a user's uploads also cancels their pending retry timers. Clearing terminal history leaves active and retry-waiting requests intact. Disabling automatic upload retries removes automatic timers but retains explicitly requested manual retries.

For stopped-service administration, `rustysoul --retry-uploads-for USERNAME` schedules that user's saved failed uploads in the configured data directory. The command takes the installation lock and refuses to run while its daemon is active. Start the same installation afterwards; it re-offers files when the recipient returns. No administrator or Soulseek credentials are changed.

Connection establishment remains separately bounded: direct dialing can take 20 seconds and reverse control connections retain their 20-second deadline; reverse file connections allow 45 seconds for legacy clients that first try an unreachable direct route. Cancellation checks described above apply to established sockets; DNS resolution and blocked local filesystem calls are not made interruptible by this change. Delivered upload offers allow 45 seconds for an answer, matching the supplied Nicotine+ transfer negotiation budget. This is not evidence of universal Internet reachability or full real-client interoperability.

## Download stalls, pause and partial resumption

A sending peer that stops delivering file data receives a 30-second inactivity budget, checked through one-second connected-socket polls. A real inactivity timeout now becomes `timed_out`, rather than a generic `failed` record. The partial remains for retry, the download slot is released, and existing timeout filters/history clearing/manual retry apply. Automatic retries remain enabled by default and use the saved bounded attempt/delay policy; while scheduled the visible state is `retry_waiting`. TCP connect and handshake I/O timeouts use the same timeout classification; local storage errors remain failures/storage holds.

Pausing keeps the current transfer connection and partial. One socket read may already be in flight; after that poll settles, disk writes stop until Resume. Time spent paused, waiting on our own speed limits or writing a local chunk does not consume the remote inactivity budget. Resume on the same connection continues; a failed partial explicitly retried after daemon restart requests its exact on-disk offset. Only newly read payload is added to lifetime counters, not the offset.

Cancellation signals the worker and cleans up its partial when its connected-socket poll settles. The worker retains its own parent-directory descriptor on Linux, so retiring the daemon's capability descriptor cannot strand cleanup. Idle cleanup must acquire the partial's file lock; active writers own their cleanup. Removal occurs while locked, with an inode/device identity check on Unix so an old worker cannot delete a replacement partial at that pathname. A missing retired download record is cancellation, rather than a false Token not found error. Unrequested late offers remain rejected. DNS, connection establishment and blocked filesystem calls retain the separate limits described above.

Expected remote disconnects, short transfers and timeouts are logged as warnings with the cause; actual local path/file/locking failures remain errors. `tests/fixtures/download_control.rs` drives independent P/F frames through pause/resume, cancelled paused data, a denied late offer, premature EOF, daemon restart and exact partial resumption, then verifies final bytes, durable counters and integrity. Independent-client coverage and remaining boundaries are documented in TESTING.md.


Transfer slot scheduling now distinguishes remote queue waits from accepted offers/active sockets. Remote waits do not starve other users. Atomic admission and a 30-second accepted-offer lease enforce local limits; offers deferred only for capacity return to waiting without network retry cost. Selected/per-user cancellation covers local waits, paused sockets and retry jobs without touching completed files. Local priority/manual order affects subsequent requests/offers and persists across restart. See TRANSFER_QUEUE.md.


Retained progress: each download attempt now shares an exact file-byte counter with its writer, including a resumed prefix. Failure, timeout and storage holds retain this count independently of periodic speed notifications; the final short fragment is included. Unopened retries preserve saved progress until a file is actually opened, and a known zero after truncation/recreation resets it. Counters are private to each attempt so old workers cannot change a retry. Terminal speeds stay zero. Both transfer lists show readable transferred/total bytes, with exact byte values available through the progress accessibility text and tooltip. These file progress values include resumed bytes; lifetime bandwidth counts only newly transferred payload. Abrupt shutdown still resumes from the actual partial on disk rather than trusting a saved UI count.


Empty files use the same offer, file-token and zero resume-offset handshake as other files, then complete without waiting for any payload or another EOF. Sharing, selection, history and readable destination paths include zero-byte files. They consume no payload bandwidth. The schema-13 download-table migration retains original rowids and every history field so default FIFO/manual queue order stays intact. Completed empty files show 100% progress; Open offers Save file without an audio decoder.


## Transfer timing

Upload and download rows display a local date/time beneath their status and a live `Elapsed HH:MM:SS` counter, with days for longer transfers. Completed, cancelled, failed, timed-out, blocked and interrupted transfers display a frozen total. Timestamps are persisted in SQLite and included in backups. The first observed active transfer starts the clock; pending queue time is excluded. Pauses and automatic retry waits are included as wall-clock time. A manual retry after a terminal result resets timing for the new attempt. Recovered interrupted transfers stop at the last saved live update, so daemon downtime is not added.

Older records are not backfilled from added/updated dates because those do not establish a real start. The UI shows timing as unavailable for that history. One shared browser clock updates mounted live rows; finished/collapsed rows do not add timers or API polling.


Live upload rates use recent payload progress, with the page header retaining its five-second average. A stalled transfer drops to zero speed; previously sent bytes or a resume prefix do not imply ongoing traffic. A server-confirmed offline requester fails its uploads and releases its slots. Broken connections and silent file receivers retain the socket failure/stall deadlines; closing an idle control connection alone does not mean the file connection has failed. Upload terminal states remain in memory until their exact observation has been saved. The daemon also reconciles persisted live rows against a complete SDK snapshot, marking abandoned uploads failed with zero speed while preserving their byte counts and history.


Upload-offer responses are matched by requester and transfer token across replacement control connections. A downloader replying `Complete` is recorded completed with no new payload traffic; `Cancelled` or `Disallowed extension` releases the slot as cancelled; other rejections fail immediately with the peer's reason. These replies never wait for the silent-offer timeout. Duplicate accepts cannot start another transfer, and another username cannot accept or reject the offer. Declines are available in protocol activity when INFO logging is enabled. Offered uploads show a detail explaining that the slot is reserved while waiting for an answer.

A queued user can close an idle control socket without losing their place. RustySoul reconnects missing controls when slots are available, with at most eight outstanding address requests (also bounded by upload slots) with unanswered lookups retried after one minute. Disconnected queued entries do not occupy upload slots or become timed-out unsent offers. A mailbox-close race restores the unsent request to the queue; live file connections retain their independent failure deadlines.


Temporary write backpressure on the nonblocking Soulseek server connection is buffered rather than treated as a lost session. Short writes retain the exact unsent suffix, subsequent frames stay ordered, and incoming replies continue to be processed. Pending output is capped at 8MiB; each flush is bounded to 64KiB and 16 writes. Real I/O failures, queue overflow or 120 seconds without outgoing progress still end the session and use normal reconnection. Cancellation and disconnect prevent unsent commands from crossing into a later session.


The upload answer deadline starts only after the full offer frame has been written to the peer control socket. Buffered output and direct/reverse connection attempts have a separate 60-second delivery deadline, reported distinctly from a peer failing to answer a delivered offer within 45 seconds.

Every offer awaiting delivery is bound to the exact control actor receiving it. If that actor closes or its initial dial fails, authoritative shared state restores its unsent uploads to the queue, including commands still in its mailbox and frames only partly written. Reconnection admits them with fresh transfer tokens. Delivered and accepted offers, cancelled requests and uploads assigned to a replacement actor are not replayed. Late delivery callbacks and answers for the retired tokens are ignored. Address lookups remain bounded and do not race an outstanding server-brokered reverse connection. A stale control actor's error cannot fail a newer actor's uploads. Independent file sockets retain their existing deadlines; online server presence alone does not prove either control or file connectivity.


In Network settings, the per-user download maximum stays editable. Automatic mode displays its effective total-slot cap; entering a per-user maximum selects manual mode, which takes effect when settings are saved. Switching automatic mode off restores the saved manual value. Upload user groups start collapsed each time the page opens, and newly loaded groups inherit the current expand/collapse default.
