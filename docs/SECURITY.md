# Security boundaries and release gates

Implemented controls are tested where indicated in `TESTING.md`. They do not constitute a security audit.

- Browser access uses username/password sign-in. Argon2id hashes are stored in SQLite with random salts. Initial deployment credentials require changing both username and password; the application API enforces this gate. New passwords require at least 8 characters. Account changes verify the current password and revoke existing sessions and SSE connections. Login/account attempts are rate limited. Opaque random session credentials use an HttpOnly, SameSite=Strict cookie, scoped to /api/v1, with a 30-day expiry. HTTPS deployments set Secure through the trusted reverse proxy X-Forwarded-Proto header. Only SHA-256 token hashes persist in SQLite; refreshes and daemon restarts retain valid sessions. Cookie-authenticated mutations require the application request header, in addition to Origin/Host checks. Logout durably revokes the current session; account changes revoke all sessions. API bearer clients remain supported. Tokens are not placed in URLs or browser storage. One administrator account is supported; there are no roles.
- Native HTTP binds to loopback by default. Remote binding requires explicit configuration. Host validation protects the default loopback deployment against browser DNS rebinding. Origin checks reject cross-origin browser requests. No CORS opt-in is provided.
- HTTP responses set CSP, frame restrictions, content-type protection, referrer policy and no-store. React escapes peer text. The static server exposes only embedded assets, never the filesystem.
- Input validation rejects traversal and bounds names, messages, requests, control queue, result views and SSE clients. Dedicated private download directories reduce local path collision and symlink risks. The data directory must be private, and an instance lock prevents two daemons using it concurrently.
- SQLite uses prepared parameters and foreign keys, stores account credentials encrypted with ChaCha20-Poly1305 and only hashes of browser/integration tokens, and refuses unknown newer schemas. Messages and file metadata are unencrypted at rest. Credential encryption protects database-only copies; access to both the database and credentials.key permits decryption. Use appropriate host/disk protection and keep backups private.
- The container runs as UID/GID 10001 with a read-only root filesystem, no Linux capabilities, no privilege escalation, and a persistent data volume. Shares should be read-only. Native systemd hardening is supplied separately.
- The native installer uses a separate static service account and private state/configuration directories. A tested systemd unit makes the filesystem read-only except for private state, temporary storage and configured downloads; library writes are rejected. Existing media are never recursively chowned by the installer. Native and container state are independent. Browser storage contains appearance/banner, section and sort preferences only, never administrator session credentials or Soulseek passwords.

Soulseek credentials and peer traffic use the legacy network protocol; this project does not add end-to-end encryption to it. MD5 checksums used by that protocol are interoperability requirements, not modern password protection. HTTPS protects the browser-to-daemon connection only.

Before a production release:

1. Review the protocol dependency's parser allocations, decompression limits, task/thread lifetimes, peer identity matching, address validation and local-network reachability. Its use of OS bindings and native SQLite lies outside this project's `unsafe_code = forbid` boundary.
2. Fuzz all accessible message paths, including compressed listings, integer boundaries, truncation, unknown messages and unsolicited transfer offers. Test symlink replacement and overwrite races against actual transfer code.
3. Test disconnect/reconnect, displaced sessions, failed authentication, slow clients, connection exhaustion and graceful shutdown during active transfers and indexing.
4. Measure and cap upload history, queue sizes, whole-library indexing, burst responses, disk usage, and connection workers in extended hostile-network tests. UI limits do not prove whole-process memory bounds.
5. Add disk reservation/quota checks, ban/ignore controls, per-command outcomes, and token/session rotation. Total/per-user upload and download rate/concurrency controls are now implemented and fixture tested.
6. Validate the container image, mounts, non-root permissions, health checks, signals and deployment templates on Docker and rootless Podman.

Dependency scans detect known advisories only. Do not infer security from the implementation language or a clean advisory scan.


Profile images accept only decoded JPEG/PNG under explicit input, dimension and allocation limits; newly uploaded pictures are re-encoded PNGs without metadata, alpha loss or lossy quantization. Expensive maximum compression runs in one bounded worker outside the daemon control loop; admission occurs before buffering large bodies and remains held even if an HTTP request disconnects. Peer picture retention is capped at 3 MiB per picture and 16 MiB across the SDK cache. Public text is rendered as text. Public profile/interest publication is distinct from administrator and Soulseek credentials. Automatic Away replies are optional (blank by default), rate-limited per sender and capped in memory. Peer capacity includes retired actors until they finish, and handshake threads are separately bounded; the configured cgroup task limit is retained. SQLite write transactions acquire the writer reservation before reading their write snapshot, preventing read-to-write snapshot-upgrade races across library/auth/control writers.


Media uses capability-scoped filesystem access within the recorded download destination, authenticated same-origin endpoints and at most four 64-KiB buffered readers. Download completion links without replacing existing names, records the destination before removing staging and recovers a crash between these steps by inode identity. Linux workers keep a directory descriptor open and use no-follow, exclusively locked partial files. Profile picture bytes are bounded, decoded under allocation limits and normalized before browser delivery. Sharing eligibility relies on reported metadata; it is configurable abuse deterrence, not cryptographic proof of reciprocal sharing or accessibility.


Operational history is authenticated administrator data in the private SQLite database, with bounded retention and queue/message sizes. The protocol observer persists warnings/errors only; raw debug/trace protocol buffers can contain credentials and are excluded. Activity records use fixed operation labels rather than serializing command bodies. UI log messages are rendered as text. Full logs still contain peer names, paths and network addresses and should be treated as private. Incoming transfer offers require a matching queued request, unchanged size and a non-conflicting token; reused tokens update in place. Unmatched file connections are discarded without starting a download worker, and pending registration retains handshake admission capacity.

Discovery uses the existing authenticated command/status boundary and fixed activity labels. Topic text is bounded to 80 bytes and rendered literally; usernames pass the normal identifier validation. There is no HTML supplied by discovery results. One discovery query runs at a time with separate bounded response lists and a 20-second timeout. SQLite retains 12 account-scoped queries and 256 public-interest profiles; the SDK bounds its fresh event backlog and topic/user caches. Cached interests and discovery history are private local administrator data even though published likes/dislikes are public on Soulseek. Community scores do not validate file availability, peer identity or sharing behavior. The legacy discovery protocol has no request identifiers, so a retry of an identical request cannot authenticate response freshness.

Private-room changes require current server-confirmed roles; cached ownership/operator flags cannot authorize actions after reconnect. Operators cannot remove the owner or other operators, and only owners can change operator privileges. Destructive membership/role changes have explicit UI confirmations in addition to backend permission checks. Private autojoin requires a complete live room list confirming membership. An unexpected public response to a private join is left immediately. Incomplete private room lists and access rosters are discarded rather than interpreted as authoritative empty/partial permissions. Invitations default disabled and are configurable per account. Room-board text is bounded and rendered literally. Cached boards and access lists are private local administrator data; room membership restricts server access but does not encrypt chat traffic. Server acknowledgements have no correlation IDs and detailed rejection text is not guaranteed, so the UI preserves observed state until confirmation and reports unconfirmed requests.


Operational metrics require normal administrator authentication, including initial-account replacement and session revocation. No public exporter or new credential type is added. Metric labels and families are fixed and exclude private paths, usernames, chats, search terms, errors and credentials; status details remain administrator data. A single 256 KiB-stack worker samples known process/cgroup/configured filesystem paths and read-only SQLite counts every five seconds. Its update wake queue holds one item, samples replace the previous in-memory view, database busy waiting is capped at 250 ms, and no samples are persisted. Potentially slow filesystem reads cannot occupy HTTP workers or the protocol control loop. A blocked probe can leave the one sampler delayed; stale timestamps remain visible and do not prevent shutdown. External monitoring sessions currently carry administrator permissions, so collectors must protect and renew them.

Download storage protection uses authenticated settings and descriptor-based capacity probes. Shared per-filesystem credits and pending writes prevent concurrent daemon downloads spending the same observed bytes twice, including writes racing capacity samples. Unknown/stale checks wait; no media is removed automatically. It is a best-effort floor rather than a quota or guarantee against external writers, inode exhaustion or delayed allocation. Expected holds are queue state, not protocol error log entries. See STORAGE_PROTECTION.md.

Upload sockets use short read/write polls plus independent handshake/inactivity deadlines. Partial offset trickles cannot hold a handshake indefinitely, and cancellation can release a connected worker without waiting for the full peer deadline. No new worker, dependency or unbounded buffering is introduced. Cancellation already published to the UI cannot be overwritten by a late worker or broker failure. Timeout/disconnect warnings remain visible in authenticated activity history; actual file I/O errors are retained as errors. Connection establishment and local filesystem blocking remain separately bounded/limited as documented in TRANSFER_RELIABILITY.md.


Backup endpoints add current-password confirmation for export/restore, normal account/session/CSRF gating, serialized work and authenticated streaming downloads. Multipart part headers are bounded at 8 KiB before Multer buffering; encrypted inputs, SQLite row lengths, image/settings checks, disk admission and operation deadlines are bounded. Credentials and the vault key are encrypted together in portable `.rsb` exports; backup passphrases are not persisted. Import requires exact supported schema, integrity/foreign-key checks and installation-scoped folder/queue validation. Journalled stopped-daemon restoration preserves the previous database/key together. Media/config are excluded; restored startup connectivity is disabled and sessions revoked. Private plaintext temporary/rollback files rely on existing mode-0700 data access. See BACKUPS.md for retention, format primitives and the lack of an independent cryptographic audit.

External integration keys are opt-in through Settings > API access. Cryptographically random 256-bit secrets are shown once, hash-only in an installation/admin-bound mode-0600 companion SQLite database, and excluded from portable backups. Read/control scopes use a default-deny route allowlist; neither can manage administrator sessions/credentials, API keys, backups or database maintenance. Control remains broad application access, including Soulseek account/network/sharing settings. Password confirmation gates enable/create; immediate revocation, expiry, global disabling, account change and backup restoration terminate access and event streams. See [API access](API_ACCESS.md).
