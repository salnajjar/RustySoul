# Download storage protection

Settings -> File locations & library -> Download storage protection sets the minimum free space on download filesystems. The default is 1 GiB, including when upgrading settings saved before this feature. Set 0 to disable the configured floor. Values use binary GiB in the UI and whole MiB in the API; fractional GiB round to the nearest MiB.

Downloads that cannot proceed show **Waiting for storage**, keep partial files, free their download slot and resume automatically when space becomes available or the reserve is lowered. This does not spend network retry attempts. Pause and Cancel remain available for held downloads while Soulseek is offline. Paused/cancelled files stay paused/cancelled when space returns. A row links directly to the relevant settings. Whole-history system counts and authenticated metrics include `waiting_for_space`.

The scheduler uses cached capacity before negotiating transfers; it allows a small initial buffer (up to 64 KiB) rather than requiring room for the whole file. The file writer checks available unprivileged space, sharing credits and pending reservations across concurrent files on each filesystem. It probes at least every 250 ms or 1 MiB of released writes; fresh credits can serve simultaneous writers while another probe runs. Writes completed during a probe remain conservatively accounted for. A single existing system sampler refreshes registered destinations every five seconds; no new worker or capacity history is added. At most 64 distinct filesystems are monitored, with directories deduplicated by device identity. Directory descriptors do not pin deleted download files.

A normal reserve hold waits at least five seconds before another negotiation; actual full/quota errors use thirty seconds. A reserve change clears these cooldowns. Pending checks, stale samples or unavailable measurements hold downloads rather than assuming there is capacity. An unavailable filesystem remains visible in system diagnostics. Already completed files and uploads are not affected.

This is a best-effort free-space floor. It does not reserve the whole queue or enforce filesystem/user quotas. External writers, allocation overhead, delayed allocation, inode exhaustion and network-filesystem behavior can still cause capacity errors. Actual full/quota errors encountered by the transfer writer retain partial progress and become storage holds even if the configurable floor is disabled. API/database state needs writable storage of its own. Manual cleanup and a filesystem quota/monitoring policy remain useful. Existing files are never deleted to make room.
