# API v1

Sign in with `POST /api/v1/auth/login` and JSON `{ "username": "...", "password": "..." }`. The response contains an opaque `token` and `account` metadata (`username`, `must_change`). Other API endpoints accept `Authorization: Bearer SESSION_TOKEN` or the browser session cookie. Browser sign-in needs no manually configured API token. Optional named integration keys are configured in Settings > API access; see [API access](API_ACCESS.md) for scopes, expiry, revocation and the management endpoints. The public browser shell and `/health` expose no account/network state. Use HTTPS for remote connections.

If `must_change` is true, only `/api/v1/auth/me`, `/api/v1/auth/account`, and `/api/v1/auth/logout` are permitted. `POST /api/v1/auth/account` requires `current_password`, `username`, and `password`; it returns a new session and revokes existing sessions. During initial setup both username and password must differ from the deployment values. After setup either can be changed; the password field is always required. `POST /api/v1/auth/logout` revokes the session. Sessions last 30 days and persist across daemon restarts. Login/account requests allow a burst of ten attempts, replenishing one attempt per six seconds globally.

| Method | Path | Response |
|---|---|---|
| GET | `/api/v1/browse/files` | Authenticated paged share files/folders; see below |
| GET | `/api/v1/status` | Current connection, shares, searches/results, transfers, rooms, messages and browse listings |
| GET | `/api/v1/events` | SSE `state` events with the same snapshot shape; initial snapshot immediately, then changes; 15-second keepalive |
| POST | `/api/v1/commands` | `202 {"status":"queued"}` after validation and enqueueing |
| GET | `/api/v1/folders?path=...` | Authenticated directory listing within installed roots; omit path to list mounts |
| POST | `/api/v1/downloads/batch` | `{ "files": [{ "username":"peer", "path":"Music/track.flac", "size":123 }] }`; 1–256 items, at most 2 MiB |

`202` acknowledges queue admission, **not completion**. Read `connection`, transfer states and the `error` field through status/events to observe outcomes. Command IDs and per-operation acknowledgments are not yet implemented. The queue holds 32 commands; its rate limit allows a burst of 10 and replenishes one command per two seconds. Invalid command fields are rejected.

```sh
curl -H "Authorization: Bearer $SESSION_TOKEN" http://127.0.0.1:8484/api/v1/status
curl -N -H "Authorization: Bearer $SESSION_TOKEN" http://127.0.0.1:8484/api/v1/events
curl -H "Authorization: Bearer $SESSION_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"type":"search","query":"artist album"}' \
  http://127.0.0.1:8484/api/v1/commands
```

Command bodies:

| Type | Additional fields |
|---|---|
| `connect`, `disconnect`, `refresh_rooms`, `rescan_shares` | none |
| `dismiss_messages` | none; clears current daemon error/notice without changing network or transfer state |
| `clear_transfers` | `direction`: downloads/uploads, `status`: all/completed/failed/cancelled/interrupted/timed_out; only finished/history records are removed |
| `search` | `query`: nonempty text, at most 256 bytes |
| `forget_search` | `id`: search UUID |
| `download` | `username`, `path`: peer virtual filename, `size`: bytes |
| `transfer` | `username`, `path`, `action`: `pause`, `resume`, `cancel`, or `remove` |
| `browse`, `close_browse`, `lookup_user` | `username`; own browse/lookup work offline |
| `set_buddy` | `username`, `buddy`: boolean; up to 128 persistent buddies |
| `update_library_settings` | `settings`: `{ "index_on_startup": false }` |
| `join_room`, `leave_room` | `room` |
| `send_message` | `target`: username or room, `text`, `private`: boolean |
| `set_away` | `away`: boolean |

Searches collect for 30 seconds; the configurable default is 100,000 stored files per search with paged results. Browse requests time out after 45 seconds and cache up to 1,000,000 validated files per user by default, with no eight-listing ceiling. SSE carries at most 100 preview files per listing. The protocol dependency can temporarily hold more results than these display limits. Usernames must be printable ASCII with no surrounding spaces, at most 30 bytes. Messages are limited to 2,000 bytes. Download paths reject traversal, absolute paths, drive prefixes, control characters, and trailing separators. Sizes must be 1 byte through 16 TiB. Active transfers must be cancelled before removal.

Typical errors: `401` invalid/missing token, `403` untrusted host/origin, `413` body above 8 KiB, `422` invalid input, `429` command/stream limits, `503` stopped worker. Framework JSON parsing errors may use plain-text responses. API evolution and machine-readable schema generation are outstanding release work.

`update_network` takes `settings`: `port`, `upnp`, `auto_reconnect`, `connect_on_startup`, `upload_slots` (0–16), `download_slots` (0–32), `upload_slots_per_user` (1–16), `download_slots_per_user` (1–32), `max_peers` (1–256), `upload_limit_kib`, `download_limit_kib`, `upload_per_user_limit_kib`, `download_per_user_limit_kib`, and `user_limits` (up to 32 unique `{username,upload_limit_kib,download_limit_kib}` entries). Speed fields range from 0 to 1,000,000 KiB/s; zero means unlimited. Missing fields receive defaults so saved older settings remain compatible. `check_network` takes no fields. Snapshots include `network`, `connectivity`, `http_bind`, `port_binding.fixed_port` (null for a directly configurable listener), total `transfer_capacity`, and optional room `last_activity` Unix seconds (only observed room messages).

Batch admission validates every item and available queue space before adding records, skips duplicate peer/path pairs, and saves local waiting entries before negotiating. The scheduler applies total and per-user reservations before requesting peer files. New local statuses are `waiting` and `paused_waiting`. Individual negotiations can subsequently fail. The dedicated batch route overrides the ordinary 8 KiB request limit; it still requires a configured administrator session and consumes one command-rate allowance. Finished-record clearing retains active/waiting/paused entries and never deletes downloaded files. Library-queued notices clear on scan completion/failure; other informational notices expire after six seconds.

`library` now includes `phase` (queued/preparing/scanning/saving/building/idle/failed), `scan_id`, `processed`, `folders` and `bytes`, alongside changed/skipped/removed/indexed counts and elapsed time. `indexed` remains the last completed total until a successful commit; `processed` is the current scan count. Directory walking has no known denominator until it finishes, so clients should use an indeterminate indicator rather than a percentage. Updates are coalesced and throttled; normal status/events endpoints carry them. A failed or cancelled scan retains the previous committed index. Browser theme/banner preferences are non-sensitive browser-local settings, separate from administrator sessions.

Credential management: `update_credentials` accepts `username` and `password` (string, or null to keep the saved password for the same username). `clear_credentials` removes the saved account. Both require disconnection. Snapshots contain `credentials_configured` and `credentials_revision`, never a password. These changes update local login credentials; they do not change the password on the Soulseek server.


`GET /api/v1/browse/files?username=NAME&offset=0` returns `{files, folders, total, offset}` with up to 100 files. Optional `folder` selects an exact virtual parent folder; `filter` performs literal case-insensitive path filtering (256-byte limit). `folders=true` instead pages folder paths and file counts, with its own filter and offset. Offsets are bounded to 2,000,000. A listing must first be opened through `browse`; closed/unknown usernames return 404. It is a metadata API and never accepts host filesystem paths.

Snapshots include `users` (presence, existence, pending/error, share statistics and optional peer description/queue data), `buddies`, `room_members`, `library_settings`, and each browse listing's `total`, `revision`, `pending` and `error`. Presence is session-only, uses bounded server watches and resets to unknown after disconnect. Unknown is not offline; not_found requires an explicit negative WatchUser reply. Subscriptions are limited to 512, with lookups/buddies prioritized and eight new watches per control tick. Explicit lookups are bounded to 32 recent users. Peer profile timeouts do not discard server statistics. Own shares use the cached local index, including while disconnected.

New network settings default `connect_on_startup` to true. Library settings default `index_on_startup` to false. Both persist through UI changes; the latter does not disable filesystem hooks or 60-second reconciliation. Buddies and normalized browse pages are stored in schema v5. Public browsing remains an exact username lookup; Soulseek provides no global substring username directory in this workflow.


Session and transfer analytics additions:
- Browser login/account responses set an HttpOnly, SameSite=Strict, 30-day session cookie. Use same-origin credentials. Cookie mutations require `X-RustySoul-Request: 1`; bearer API clients still work. `GET /auth/me` restores account identity after refresh.
- `GET /transfers/{downloads|uploads}?status=all&filter=&order=activity&reverse=false&offset=0&limit=100&group_users=false` returns durable records, a matching total and all-record summary/clearable counts. `limit` is a 1..1000 row budget (default 100). `group_users=true` orders users by the first matching file in the requested order (or the selected `user_sort`) and admits whole matching user groups; a group can exceed the row budget without truncation. Use the returned `next_offset` for subsequent requests, starting at zero; arbitrary offsets inside groups are not valid group boundaries. Responses use a single read transaction for consistent files/counts/metadata. The UI appends on scroll and replays its loaded window after live revisions, deduplicating identities. There is no UI history-page or 2,500-file cutoff. Order supports activity, speed, progress, eta, remaining, size, name, folder, user, status, queue, local_queue, added and updated. `queue` is the reported peer position; `local_queue` sorts saved priority descending then local order. Transfer records include `priority` (-1 Low, 0 Normal, 1 High) and `local_queue_order`. Unknown ETA/queue values stay last.
- `GET /traffic?from=<UTC epoch seconds>&to=<exclusive UTC epoch seconds>` returns lifetime payload totals, logging start, effective interval and at most about 720 points. Missing buckets mean zero traffic. Coarse boundary buckets are included in full. No per-peer history is recorded.
- `download_folder` takes username/folder/recursive and admits the complete cached branch atomically, subject to queue capacity. `update_retry_policy` takes settings (enabled, max_attempts, base_delay_seconds, max_delay_seconds). Retries default enabled.


Profile/resilience additions:
- `GET /profile` returns your editable profile; `POST /profile` accepts description, picture (base64 JPEG/PNG or null), likes/dislikes arrays, away_on_startup and away_message. The authenticated endpoint allows up to 14 MiB of JSON for a JPEG/PNG input of up to 10 MiB (24 million pixels, dimensions at most 32768, decoded allocation capped at 96 MiB). A single blocking worker shrinks only when needed to fit 512x512, applies JPEG orientation and writes a metadata-free lossless PNG with maximum oxipng/Zopfli compression. Alpha and 16-bit samples are preserved; there is no lossy quantization or enlargement. Other requests keep their normal limits and deadlines; this endpoint allows 180 seconds. Concurrent profile uploads return 429 before buffering their bodies. The processed update is queued with a revision check; a changed profile rejects a stale update. Profile metadata/revision is included in status; picture bytes are fetched separately and never included in SSE snapshots.
- Transfer queries also accept `user_sort=most|least|oldest|newest|recent|name` (empty follows file order). The response adds `users` with independent lifetime payload totals, first/latest sample dates and matching history counts, plus `users_since` for attribution start. Sorting covers the entire matching history.
- Status includes `effective_peer_limit`, adapted to the cgroup thread budget. Requested network settings remain editable. Ordinary capacity backpressure is a debug event; actual resource failures remain warnings.


Sharing/media/rooms additions (schema 8):
- `GET /users/picture?username=NAME&v=REVISION` serves a bounded PNG (or a previously saved JPEG) for your own or an opened profile; no picture returns 404. Authentication and initial-account setup are required. Pictures are excluded from SSE.
- `GET` or `HEAD /downloads/file?username=NAME&path=REMOTE_PATH` streams a recorded completed file. Single byte ranges support seeking; invalid ranges return 416. `download=true` requests an attachment. No arbitrary local path is accepted. Paths stay inside the recorded download root, streams are bounded to four simultaneous readers, and missing/moved files return 404.
- `update_sharing_policy` accepts `settings`: mode (`off`, `sharing`, `buddies`), min_files, min_folders, exempt_buddies, exceptions, allow_unknown, check_seconds and cache_seconds. `sharing` with one file, buddy exemption and decline-on-timeout is the default. Upload history includes `checking_shares` / `blocked` and a readable detail; clear-history accepts `blocked`.
- `POST /rooms/read` accepts `{room, through_id}`. Cursors are monotonic and cannot acknowledge future messages. This endpoint has its own bounded rate budget and requires normal authentication/CSRF protection. Snapshots contain stable message IDs, subscribed_rooms, room_read and room_unread. Explicit Join/Leave persists subscription intent; live membership resets on disconnect and rejoins after authentication.


Workspace/logs additions (schema 9):
- `GET /logs?level=all&source=all&filter=&before=0` returns up to 100 newest entries and `more`. Entry fields: id, at (UTC seconds), level, source, message. Use the last entry ID as `before` for older history. Normal authentication and initial-account gating apply. Retention is seven days/10,000 entries, with 4,096-character messages and a bounded writer queue. Protocol debug packet buffers and command bodies are excluded.
- `POST /downloads/batch?confirm=true` waits for daemon admission and returns 202 with `{status:"queued", files:N}` only after intent has been persisted. Admission rejection returns 409; timeout returns 503 and advises checking the queue before retrying. The original endpoint without confirmation retains its asynchronous contract. Selection limits remain 1–256 files and available active queue capacity.
- `restart_search` takes id/query, retains the previous scope and replaces its cached results using a new protocol token. `retry_downloads` takes nullable username, retrying failed/timed-out/interrupted downloads subject to queue capacity. `cancel_uploads` takes username and paths (up to 256); an empty paths array cancels every currently active/queued/offered upload for that user across pages.
- `/browse/tree` folders now include `subfolders` (all descendants) and `direct_folders` alongside recursive file totals. Saved peer-library tabs no longer have an eight-user ceiling.

Social discovery additions (schema 10):
- `discover` takes `query: {mode:"personal"}`, `{mode:"popular"}` or `{mode:"topic",item:"jazz"}`, plus verified shared-dislike discovery `{mode:"dislikes",item:"noise"}`, plus optional `refresh` (default false). Topics are nonempty, at most 80 bytes, normalized to trimmed lowercase. A non-refresh query opens a cached result when available, including offline; otherwise it requests the server. Refresh requires a connected session. Only one discovery request is active at a time; personal/popular/topic queries have a 20-second deadline; shared-dislike discovery has a 40-second deadline. Commands retain the normal authenticated asynchronous admission contract.
- Snapshots contain `discovery`: query, recommendations/against (`item`, signed `rating`), people (`username`, nullable `weight`), separate recommendations_at/people_at UTC-second timestamps, pending flags and nullable errors. Personal people carry similarity weights; per-topic replies supply names only, so their weight is null. Empty completed replies have timestamps and empty lists. Unmatched/unsolicited replies do not replace the current view.
- `set_interest` takes item (up to 80 bytes) and disposition (`like`, `dislike`, `remove`). It atomically edits the persisted current profile, preserves its picture and other fields, removes the opposite disposition and publishes changes when connected. Existing profile limits apply: 100 likes and 100 dislikes. Changes made offline publish on login. Refresh personal discovery after editing interests.
- `lookup_user` also requests public interests via the server, independently of peer profile availability. User views add `interests: {likes,dislikes,updated_at}`, `interests_pending` and `interests_error`. Public interest caches are bounded to 256 profiles; discovery caches to 12 account-scoped queries. Up to 500 valid entries per reply list are retained, and transient pending/error state is excluded from stored discovery results.

Room control additions (schema 11):
- `set_room_invitations` takes enabled (boolean); intent persists per network account even offline and is sent on login. Snapshots expose desired accept_invitations, nullable invitations_confirmed and invitations_error under room_management. New accounts default to declining invitations.
- `create_private_room` takes room (the normal 1–24 ASCII room-name validation). It requests code-14 private creation/join and persists separate private subscription intent. Known public names are rejected; unexpected public replies are left immediately. Ordinary `join_room` joins a known private membership without requesting creation. Private automatic rejoin waits for a complete live server membership list.
- `private_room_action` takes room, action (`add_member`, `remove_member`, `add_operator`, `remove_operator`, `leave_membership`, `resign_operator`, `relinquish_ownership`) and optional username. The first four actions require a username; own-role actions reject one. Ownership/operator permissions are checked against current server state, with additional restrictions on removing owners/operators and promoting non-members. Administrative roster changes require joining the room first. This does not provide a transfer-ownership command.
- `set_room_ticker` takes room/text (empty clears; otherwise up to 512 bytes with no control characters). The room must be subscribed or joined. Intent persists per account/room; publishing occurs while joined and on subsequent joins. Snapshots expose pending/error separately from intent and observed board contents. Requests use the existing asynchronous command admission contract, with a 20-second confirmation deadline; late matching confirmations can clear obsolete errors.
- `GET /rooms/entries?room=NAME&kind=board|member|operator&filter=&offset=0` returns total, offset and up to 100 entries containing username, text (empty for access lists) and operator. Reads use the current network account and normal administrator authentication/initial-account gating. Counts, owner/role, cached/live flags, timestamps and a revision appear under room_management.rooms in status/SSE. Whole rosters and boards stay out of snapshots. Limits and confirmation semantics are documented in FEATURES.md.

Chat emoji are ordinary UTF-8 text in the existing `send_message` command and room/private protocol strings. The 2000-byte limit applies to UTF-8 bytes, including combined emoji sequences. No custom reactions, stickers or HTML are sent.

Text-emoticon conversion is a browser display feature. API/SSE and SQLite retain original message text. Native selection/copy of a converted message produces Unicode emoji, which the existing UTF-8 `send_message` command accepts unchanged. No new message type or API transformation is introduced.


System monitoring (schema remains 11): status/SSE include a `system` object with sample timestamp, uptime, optional process/cgroup/filesystem/database readings and complete retained transfer counts/speeds. All probes run on one coalescing worker every five seconds; metrics/HTTP requests use cached values. `GET /metrics` returns authenticated Prometheus text format 0.0.4, including fixed transfer state labels and durable payload counters, without usernames/paths/message text. The initial-account gate and normal session revocation apply. Failed probes remain null in JSON and are omitted as numeric metrics; sample time/age allow delayed sampling to be detected. See MONITORING.md for names, units, parent-cgroup interpretation and collector authentication.

Download storage protection (schema remains 11): `network.minimum_free_space_mib` defaults to 1024 for new and older saved settings. `{"type":"update_storage_reserve","minimum_free_space_mib":1024}` saves only this setting; it preserves network port, concurrency and speed controls and works while disconnected. Integer range is 0 through 1,024,000,000 MiB; 0 disables the configured floor. Full `update_network` also accepts the field.

`waiting_for_space` is a persistent, non-failure download status. Transfer pages include retained byte progress and a storage explanation; filtering by this status, activity ordering and system/metrics state counts are supported. Held downloads free negotiation slots and do not consume network retry attempts. Individual pause/cancel works offline; resumption requires network connectivity and capacity. Reserve changes clear storage cooldowns. See STORAGE_PROTECTION.md for the floor's best-effort guarantees and limitations.

Upload timeout reporting: unanswered transfer offers, expired reverse connections and stalled established file connections use `timed_out` with a readable `detail`. Existing transfer status filtering, summary/metrics state counts and `clear_transfers` with `direction: "uploads", status: "timed_out"` apply. Bulk/single upload cancellation remains terminal if a late worker error arrives. Clearing records does not alter media or lifetime traffic. No schema or command shape changes are required. See TRANSFER_RELIABILITY.md for time budgets and limitations.


Encrypted backups (schema 11): all `/backups` routes require the changed administrator account, normal authentication and cookie mutation/CSRF checks. `GET /backups` returns busy/ready/can_restart/last_result. `POST /backups` accepts `{current_password,passphrase}` and returns one temporary export descriptor; `GET /backups/{id}/file` streams an authenticated attachment. `POST /backups/inspect` accepts multipart fields **passphrase first, file second** and returns a validated restore descriptor. `POST /backups/{id}/restore` accepts `{current_password,confirmation:"RESTORE"}`, stages a verified restore and requests supervised restart. `POST /backups/cancel` cancels create/inspect; `POST /backups/clear` discards the current descriptor. Invalid/wrong-password backups return 400; expired IDs return 404; another expensive operation returns 409. Status reads/cancellation remain available while busy. A restore response acknowledges a staged restart, not completed recovery; sessions are revoked after applying it. See BACKUPS.md for exact limits, folder requirements and included/excluded state.


Soulseek privileges: `check_privileges` with optional `watch_for_activation` starts/coalesces a live server check. Status/SSE add `privileges` containing official-server eligibility, nullable remaining seconds/check/expiry times, pending/watch flags and a local error. Login checks automatically; balances are account-scoped and reset on disconnect. See PRIVILEGES.md for deadlines, polling limits and purchase handoff.


Database maintenance: `GET /maintenance` returns capacity/outcome and restart state; `POST /maintenance` accepts optimize/compact and returns the queued ID. It uses normal authentication/CSRF and the shared database/backup gate. Completion is reported after the supervised restart with the same ID. Profile adds `auto_away_minutes` (0 disabled, 1..1440 enabled); `ui_activity` with optional idle_seconds reports activity age without input contents. Snapshots add away_automatic and library.trigger; only scheduled scan banners are suppressed. See MAINTENANCE.md for recovery, scheduling and presence semantics.

Shared-dislike snapshots add optional `dislike_evidence`: `checked`, `matched`, `cached`, `requested`, `timed_out`, `limited`, `missing_sources`. People are confirmed by their public dislikes; recommendation ratings count this cohort's likes and negative ratings count their other dislikes. This is a bounded verified sample, not a network-wide dislike directory. See [discovery](USER_DISCOVERY.md).


Transfer queues (schema 12): `cancel_downloads` takes `{username,paths}` with at most 256 paths; an empty array cancels all unfinished downloads for that user, including paused/retry/storage waits. It works offline, retains completed files/history and removes cancelled retry jobs. `cancel_uploads` has the same selected/all scope for uploads while connected. Large UI batches are divided under both the 256-path and ordinary HTTP body limits; accepted subsets are deselected and failed submissions remain selected.

`update_transfer_queue` takes `{direction:"downloads"|"uploads",username,path,priority}` or `{direction,username,path,movement:"top"|"up"|"down"|"bottom"}`. Exactly one of `priority` (integer -1..1) and `movement` is required. Only waiting/paused work can be edited; accepted upload offers and active files are not interrupted. Moves stay within one priority. Commands are asynchronous admissions; status/log messages report execution failures. These controls use the existing control API-key scope. Preferences are durable and included in encrypted backups. Schema-11 archives remain importable and migrate after validated restore. See TRANSFER_QUEUE.md for remote queue and privileged-upload semantics.


Retained partial progress (schema unchanged at 12): download `transferred` includes the known resume prefix and final short writes on failed/timed-out/storage-held records. An unopened retry updates speed/queue metadata without replacing its saved byte count with zero. Opening a new or truncated partial establishes a known zero. Terminal speed is zero; completed records report size. These file progress values are distinct from newly received payload/lifetime bandwidth. UI progress bars expose exact transferred/total bytes through aria-valuetext and tooltips.


Empty files (schema 13): download command/batch entries accept size 0 through 16 TiB inclusive; negative JSON sizes and larger files remain invalid. Search and browse results retain zero-byte files. GET/HEAD `/downloads/file` returns 200 and Content-Length: 0 for an authenticated empty completion; byte-range requests on an empty representation return 416 with Content-Range: bytes */0. Empty transfers still perform normal offers/offset handshakes and record completion with zero payload. Schema-11/12 archives validate against their original exact schemas and migrate to 13 only after restoration.
